# Architecture and Security

This document describes how the reference demo is built, what it deliberately does not
do, and what would have to change before anything like it ran next to real equipment.

## Scope

PlantPulse is a demonstration of an architecture, not a product. The telemetry is
generated by a simulator, the engineering data is synthetic, and nothing reads from or
writes to a controller. It must not be used as, or mistaken for, a safety system: safety
functions belong in certified safety hardware, and an information display never replaces
them.

## Components

| Component | Responsibility |
| --- | --- |
| React single-page app | Renders one plant snapshot at a time; sends simulation commands |
| Nginx | Serves the static bundle and proxies `/api/` to the backend |
| FastAPI routers | Read side (`/state`, `/stream`), matrix, alarm actions and simulation controls |
| `PlantEngine` | Owns all mutable state and composes the simulation modules |
| Simulation modules | Alarm lifecycle and history, network telemetry, production counters, event log |
| Broadcaster | Fans snapshots out to every connected stream client |
| Matrix ingestion | Writes and parses the multi-header Excel Cause & Effect workbook |

## Data flow

1. At startup the synthetic rules are written to an in-memory Excel workbook and parsed
   back. The rules the API serves are therefore the result of spreadsheet ingestion.
2. A background task advances the simulation at a fixed period (two seconds by default,
   set with `PLANTPULSE_TICK_SECONDS`) and publishes a snapshot.
3. A command such as `POST /simulate/trigger/ALM-207` mutates the engine and publishes
   immediately, so the change reaches every client without waiting for the next tick.
4. Acknowledging an alarm records the time and changes how it is shown. It does not
   clear the alarm or lift its interlock; only clearing does, and a cleared alarm moves
   to the history with its raised, acknowledged and cleared times.
5. Each stream client has its own bounded queue. The stream sends a `snapshot` event on
   connect, `update` events afterwards, and a `heartbeat` event when nothing was
   published for five seconds.

### Why full snapshots instead of deltas

Every event carries the complete state. That costs a few kilobytes per message and buys
three properties: a client is consistent after one message, a dropped message cannot
leave a client with a wrong picture, and a slow client can simply skip to the newest
snapshot. For a plant-floor display, never showing a stale alarm matters more than
bandwidth on a local network.

### Why Server-Sent Events

The data flows one way, from plant to screen. SSE runs over plain HTTP, passes through
proxies without special handling, and browsers reconnect on their own. Commands go
through ordinary `POST` requests, so nothing needs a bidirectional channel.

### Why a single worker

State lives in the process. Two workers would hold two different plants and clients
would see either one at random. Scaling out would require moving state and fan-out to a
shared broker, which this demo intentionally leaves out.

### Connection health

A proxy can keep the browser side of a stream open after the backend has died. The
browser does not report that case. The client therefore treats eight seconds without any
event as a dead connection, shows `RECONNECTING` and then `DISCONNECTED`, and keeps
retrying until the stream returns.

## On-premises posture

The stack is designed to run with no outbound network access:

- no CDN assets, no web fonts, no analytics, no third-party API calls;
- the interactive API documentation page is disabled because it would load assets from a
  public CDN (the OpenAPI schema is still served locally);
- the two containers talk over the internal Compose network and only the frontend port
  is published.

Building the images does need a registry and package indexes. An air-gapped site would
build elsewhere and import the images, or use internal mirrors.

## Security controls in this repository

| Control | Where |
| --- | --- |
| Port bound to `127.0.0.1` only | `docker-compose.yml` |
| Backend not published to the host | `docker-compose.yml` |
| Containers run as non-root, read-only root filesystem (in-memory `/tmp` only), all capabilities dropped, `no-new-privileges` | `docker-compose.yml`, Dockerfiles |
| Content Security Policy, `X-Frame-Options`, `nosniff`, `Referrer-Policy` | `frontend/nginx.conf` |
| Same-origin API through the proxy, so no CORS is enabled | `frontend/nginx.conf`, `vite.config.ts` |
| Path and query parameters validated by pattern and length | `backend/app/api/` |
| Exact dependency versions, lockfile for the frontend | `requirements.txt`, `package-lock.json` |
| Bounded per-client queues | `backend/app/simulation/broadcaster.py` |
| Upload validation before parsing (see below) | `backend/app/matrix/upload.py` |

## Uploaded workbooks

An `.xlsx` file is a ZIP archive of XML, so a small upload can hide a very large one.
The upload path therefore checks, in this order and before the parser sees anything:

1. the file name ends in `.xlsx` (the name is used only as a display label, never as a path);
2. the body is at most 2 MB, enforced while reading, not only from the declared length;
3. the content is a ZIP archive that contains a workbook part;
4. the archive has a bounded number of parts and expands to at most 25 MB;
5. the sheet spans at most 5,000 rows and 100 columns. This is checked before any row
   is read: a file of a few kilobytes can declare a million rows through one stray cell,
   and walking them would exhaust memory;
6. the parsed matrix has valid codes, severities and non-blank cells, references only
   known stations, and has at most 500 rules.

A rejected upload changes nothing: the previous matrix and the active alarms stay as
they were. A successful upload clears active alarms, because their hardware trace may
have changed, and they are recorded in the history. XML parsing uses `defusedxml`.

## Known gaps

These are accepted for a demo and would be blockers anywhere else.

- **No authentication or authorisation.** Anyone who can reach the port can inject
  faults, acknowledge alarms and replace the matrix. This is why the port is bound to localhost.
- **No TLS.** Traffic is plain HTTP.
- **No rate limiting and no cap on stream connections.** A client can open many streams.
- **No persistence or audit trail.** State and the event log are lost on restart.
- **Uploads are parsed in the API process.** The checks above bound the work, but a real
  system would parse untrusted files in an isolated worker with time and memory limits.
- **Acknowledgement is anonymous.** There are no users, so the history cannot say who
  acknowledged an alarm.
- **Build tooling advisory.** `npm audit` reports a regular-expression denial-of-service
  advisory in `picomatch`, a glob matcher used by the build tool, with no patched release
  available at the time of writing. It runs only at build time against patterns from this
  repository and is not shipped to the browser. Runtime dependencies report no advisories.

## What a real deployment would add

- **A read-only data path from the control network.** For example an OPC UA or MQTT
  gateway placed in a demilitarised zone, with the diagnostics server unable to write to
  controllers by design. Network segmentation along the lines of IEC 62443 zones and
  conduits is the usual reference.
- **Authentication and roles**, backed by the site directory, with operators able to
  view and only engineers able to change the matrix.
- **TLS** terminated at the proxy with certificates from the site authority.
- **Persistence**: alarm history and an audit trail in a database, plus backups.
- **Managed matrix changes** instead of a direct upload: version control, review and
  sign-off for every change to a Cause & Effect rule, since a wrong recommendation on a control-room screen is a hazard.
- **Alarm management practice**: priorities, shelving, return-to-normal states and
  attributed acknowledgement following a standard such as ISA-18.2, beyond the simple
  raised, acknowledged and cleared model used here.
- **Monitoring** of the diagnostics system itself, with an alert when it loses its data
  source, so a silent screen is never read as a healthy plant.
- **No simulation endpoints.** The fault injection API exists only for the demo.
